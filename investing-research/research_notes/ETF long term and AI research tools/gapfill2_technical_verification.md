## Q1 (R10, gap 5). Does a free, keyless daily data path work for TSX-listed ETFs (prices, expense ratio, holdings, FX, macro), and what are its observed limits?

### Takeaway
Yes. One batched `yfinance 1.7.0` call returned 10+ years of daily OHLCV plus `Adj Close`, `Dividends` and `Capital Gains` for every TSX ticker that has existed that long (XIC.TO from 2005-01-04, ZAG.TO 2010-01-25, VFV.TO 2012-11-08, XEF/XEC 2013-04-15, XUU 2015-02-20, XEQT 2019-08-14) and for VTI/VT/VXUS, in 2.6 s with no 429; `Ticker.info` gives `netExpenseRatio` (XEQT 0.20, XEF 0.23) and `funds_data.top_holdings` works for TSX funds; the Bank of Canada Valet API (USD/CAD, from 2017; legacy series back further), FRED `fredgraph.csv` (keyless, 1971+/1976+) and BlackRock Canada's iShares holdings CSV (8,353 lines, as of 2026-10-30, no login) all downloaded. ### Inferences
- Recommended free, keyless daily path for a Canadian ETF monitor: (1) prices/total return: `yfinance` batched `download(..., auto_adjust=False, actions=True, threads=False)` with one retry per failed ticker, run once per day and cached to CSV/parquet; (2) fund facts: `Ticker.info["netExpenseRatio"]`, `totalAssets`, `yield`, `fundInceptionDate` weekly, and `funds_data.top_holdings` as a sanity check; (3) authoritative holdings: the iShares `.ajax?fileType=csv` URL per product id (weekly), parsed by splitting on the second `Fund Holdings as of` line; (4) FX: BoC Valet `FXUSDCAD` (2017+) spliced with `IEXE0101` for earlier years, or FRED `DEXCAUS` (1971+) as a single series; (5) macro: FRED `fredgraph.csv?id=...` for T10Y2Y, DGS10, SAHMREALTIME, UNRATE with a fallback to the keyed API if the CSV route fails from the host in use.
- Observed limits: yfinance is unofficial and the threaded sqlite cache can lock; no 429 appeared in ~60 requests, but round 1's third-party reports of 429s mean the monitor should rate-limit itself (e.g., ≤1 request/s, one batch call per day) and persist data so a blocked day does not break reports. FRED's CSV route and Stooq both depend on the egress path (both failed through one proxy route), so a cloud scheduled task must have those hosts allowlisted and a fallback.
- Vanguard Canada and BMO holdings CSV patterns were not probed; the iShares pattern covers XEQT/XEF/XEC/XIC/XUU, i.e., the whole DIY candidate set.

### Gaps
- Stooq could not be reached from this sandbox at all, so its TSX coverage and symbol format remain unknown.
- Alpha Vantage `ETF_PROFILE` with Toronto symbols and the EODHD sandbox were not tested because both require a key (even free), and the working rule for this round was keyless endpoints only.
- yfinance 429 behaviour under sustained daily use from a cloud scheduled task's shared egress IP is untested; a single 15-minute probe from one IP is weak evidence.
- Vanguard CA / BMO holdings download URL patterns were not checked.
- The `Total Net Assets` unit in `funds_data.fund_operations` is undocumented (174,598.9 for a CAD 22.9 B fund).

## Q2 (R12, gap 11). Do vectorbt (open source) and bt support periodic cash contributions, and what does a contribution-aware pandas backtest of XEQT vs. a DIY mix vs. VT show?

### Takeaway
Open-source vectorbt 1.2.0 has no `cash_deposits` parameter anywhere in the installed package (0 files match; `Portfolio.from_orders`/`from_holding` signatures only expose `init_cash`), so periodic contributions must be modelled as extra orders or in VectorBT PRO; `bt 1.4.1` supports contributions natively via `bt.algos.CapitalFlow(amount)` which calls `StrategyBase.adjust(amount, update=True, flow=True)` and keeps flows out of the price index. A plain-pandas backtest of CAD 1,000/month shows XEQT (2019-09 to 2026-11, 87 contributions): ending CAD 153,112 on 87,000 contributed, XIRR 15.6 %, TWR 14.3 %/yr, max drawdown -29.7 %; the DIY 45/30/10/15 mix and VT-in-CAD land within ~1 pp of it; over the longer 2015-03 window the DIY mix returned 13.0 % XIRR vs. VT 13.2 %.

### Cited Findings
- `pip install vectorbt bt` installed vectorbt 1.2.0 (PyPI upload 2026-10-19) and bt 1.4.1 (PyPI upload 2026-10-10) — observed; [vectorbt on PyPI](https://pypi.org/pypi/vectorbt/json); [bt on PyPI](https://pypi.org/pypi/bt/json)
- `grep -rl cash_deposits <site-packages>/vectorbt` → 0 files; `grep -rni deposit` → no hits; `inspect.getdoc(vbt.Portfolio.from_orders)` does not contain `cash_deposits`; `from_holding` docstring does not either; `inspect.signature(vbt.Portfolio.from_orders)` lists `close, size, size_type, direction, price, fees, fixed_fees, slippage, min_size, max_size, size_granularity, reject_prob, lock_cash, allow_partial, raise_reject, log, val_price, init_cash, cash_sharing, call_seq, ffill_val_price, update_value, max_orders, max_logs, seed, group_by, broadcast_kwargs, wrapper_kwargs, freq, attach_call_seq, **kwargs` (no deposits/earnings argument) — observed

### Inferences
- XIRR exceeds TWR in every row because the contribution stream is back-loaded into the strong 2023-2026 period; a planner should quote TWR when comparing funds and XIRR when reporting the saver's own experience.
- The DIY mix tracked XEQT within about 1,000 CAD on 87,000 contributed over the common window, so the fund-of-funds premium (0.20 % MER vs. a ~0.1 % weighted DIY MER before withholding effects) does not show up as a large return gap in 7 years of pre-tax data; the withholding-tax layer (round-1 R4/R5) is not modelled here.
- Modelling choice for the toolkit: use `bt` when a library is wanted (CapitalFlow + `RunMonthly` + `WeighSpecified`/`Rebalance`), otherwise the ~100-line pandas routine above, which is simpler to audit and already handles multi-currency.
- Open-source vectorbt is still usable for signal research (vectorised indicators, parameter sweeps) but not for contribution accounting without manual order construction; its Commons Clause is irrelevant for personal use but blocks selling a hosted product built on it.

### Gaps
- VectorBT PRO's `cash_deposits` (which the PRO docs advertise) was not verified because PRO is paid and not installable here.
- bt was not actually executed on the data (only its API was inspected); a bt-vs-pandas cross-check of the numbers above is still open.
- XIRR/TWR differences from Portfolio Visualizer or testfol.io were not reconciled (both sites were not fetched this round).
- The backtest ignores commissions, bid-ask spreads, FX conversion costs (Norbert's Gambit vs. broker spread) and withholding taxes; VT's CAD result in particular overstates a Canadian investor's net return.

Ten-line summary:
1. `portfolio.py` (81 lines): Pydantic `PortfolioContext` (`cash`, `currency`, `positions[]` of `ticker/quantity/average_price`) loaded from a JSON file by `load_portfolio`; `render(ticker)` emits a "Portfolio at the analysis date" block and `fingerprint()` hashes the book so a resumed run cannot use a stale one; explicitly "broker-neutral" and distinguishes "no context" from "flat".
2. `agents/managers/portfolio_manager.py` (106 lines): one LLM call with `with_structured_output(PortfolioDecision)`; prompt forces a rating from `Buy / Overweight / Hold / Underweight / Sell` plus executive summary and thesis; falls back to free text and `parse_rating`; writes `final_trade_decision` and `final_rating`, marks `latest_speaker: "Judge"`.
3. `agents/managers/research_manager.py` (74 lines): judges the bull/bear debate into a `ResearchPlan` (recommendation, rationale, strategic actions) with the same 5-tier scale; "conflict alone is not a reason to Hold".
4. `agents/risk_mgmt/{aggressive,conservative,neutral}_debator.py` (68-70 lines each): pure prompt nodes; each receives the four analyst reports, the trader plan, instrument and portfolio context and the other two debators' last responses, appends its argument to `risk_debate_state.history` and its own `*_history`, and increments `count` (rounds are bounded by `max_risk_discuss_rounds`).
5. `agents/trader/trader.py` (98 lines): turns the research plan into a `TraderProposal` (action Buy/Hold/Sell, numeric entry price and stop-loss "never a percentage", position sizing) grounded in the technical market report.
6. `agents/rating.py` (117 lines): canonical `RATINGS_5_TIER`, regex parsers for "Rating: X" lines, and a `RATING_REVIEW = "REVIEW"` sentinel returned when no rating is found, "rather than a tradeable position ... a decision nobody can read is not a Hold".
7. `agents/schemas.py` (379 lines): the Pydantic models `ResearchPlan`, `TraderProposal`, `PortfolioDecision` (rating, executive summary, thesis, optional price target and horizon) and `SentimentReport` (band, score, confidence, narrative).
8. `reporting.py` (136 lines): `write_report_tree(final_state, ticker, save_path, settings, html)` writes `1_analysts/*.md`, `2_research/{bull,bear,manager}.md`, `3_trading/trader.md`, `4_risk/{aggressive,conservative,neutral}.md`, `5_portfolio/decision.md` and `complete_report.md` with a provenance header (analysis date, rating, generation time, version, deep/quick model per provider, analysts, debate rounds, data vendors, memory log); `report_html.py` renders the same tree to one self-contained `complete_report.html`.
9. `backtest.py` (236 lines): `run_backtest` iterates the graph over a ticker x date grid into a memory log, `summarize` scores settled decisions by rating against later prices (`_alpha`), so it is a decision-quality harness, not a portfolio simulator.
10. Reusable in a monitor that never trades: items 1, 6, 7 (schemas minus the trader proposal), 8 and the debate-state bookkeeping of item 4 as a report-generation graph; not reusable: the trader's entry/stop proposal, `backtest.py`'s price-alpha scoring (single-stock, short horizon), and the exchange/broker wiring referenced from `graph/`.

## Q5 (R14/R9, gap 6). What network access and secrets does a Claude Code cloud scheduled task get, must data-vendor hosts be allowlisted, what is the minimum interval, and how are outputs written back to GitHub?

### Takeaway
A scheduled task inherits its cloud environment's network policy; the Default environment is "Trusted", which allows only a 204-domain allowlist of Anthropic, GitHub, package registries and cloud-provider hosts — no `query1.finance.yahoo.com`, `fred.stlouisfed.org` or `bankofcanada.ca` — so a data-fetching task needs a Custom allowlist (one domain per line, wildcards allowed) or Full access; API keys should go in "network secrets" (attached by Anthropic's proxy outside the VM) rather than environment variables, which "anyone who uses the environment can read"; cron expressions "that run more often than once per hour are rejected"; each run clones the repo fresh, starts from the default branch and "pushes its work to a branch prefixed with `claude/` unless your prompt directs it to push to another branch", with commits carrying a `Claude-Session:` trailer.

### Inferences
- A daily ETF-watch scheduled task needs a Custom environment whose allowlist includes at least `query1.finance.yahoo.com`, `query2.finance.yahoo.com`, `fc.yahoo.com` (yfinance's cookie/crumb hosts), `fred.stlouisfed.org`, `www.bankofcanada.ca`, `www.blackrock.com`, plus the defaults for `pip install yfinance`; keyed vendors (EODHD, Alpha Vantage, FRED API) are best wired as network secrets on their hosts, which also opens those hosts without touching the allowlist.
- Workable cron specs: daily `7 22 * * 1-5` (22:07 UTC = after TSX close, 17:07 ET during EST; use `CRON_TZ=America/Toronto 7 17 * * 1-5` to avoid DST drift) and monthly `17 13 1 * *`; a prompt line such as "commit `reports/YYYY-MM-DD.md` and push to branch `reports`" overrides the `claude/` prefix, with a GitHub ruleset restricting the run's push rights to that branch.
- Because the fetch route matters (FRED's CSV failed through this sandbox's proxy but not through the WebFetch route), the task's Python should retry with HTTP/1.1 and fall back to cached data, and the prompt should instruct Claude to report (not silently skip) blocked hosts, which the docs say appear "in the transcript rather than on the row".

### Gaps
- The actual run of a minimal `.mcp.json` + `daily-etf-watch` SKILL.md via `claude -p --output-format json` (audit gap 6) could not be completed: the CLI in this sandbox returned "Authentication error" with `total_cost_usd: 0`; the files were not written because a cost figure could not be produced.
- The docs do not say whether yfinance's crumb/cookie hosts (`fc.yahoo.com`, `query2.finance.yahoo.com`) must be listed separately; the host list above is inferred from yfinance's behaviour, not from a cloud run.
- Whether the security proxy's "rate limiting and abuse prevention" throttles a burst of Yahoo requests is undocumented.
